## 5. User journey map

### Journey A — Programme → Revision/MSP → Activity → Site Diary entry

Actual executable journey:

1. User manually reaches `/site-diary`.
2. `DailyEntryShell` loads active Programmes from `/api/programme?status=Active`.
3. One Programme auto-selects; multiple require an explicit in-page selection.
4. `/api/project-summary?programmeId=<id>` resolves `revision_id` as the current authorized Revision.
5. NEW uses `OperationalSourceSelector`; OPEN loads canonical open Activities for `programmeId` and continues with exact `activityId`.
6. `DailyEntryForm` creates/updates the Diary using Programme, current Revision, Activity/source, and exact persisted identity.

There is no Programme page, Revision/MSP page, or Activity-detail page. The root Activity dashboard is not a valid start to this journey because it hardcodes `prog-1` and does not carry Activity or Programme identity to `/site-diary`. Manual navigation/backtracking is required between `/` and `/site-diary`.

### Journey B — Diary management → exact current detail → edit

`/site-diary` → RECORDS → current Revision resolved by canonical `isCurrentRevision` → list item selected by `siteDiaryId` → `DiaryDetail` re-reads exact Diary and validates Programme/Revision/Activity bond → Edit passes the same `siteDiaryId` to `DailyEntryForm.initialSiteDiaryId`.

The record identity is canonical. The route is not: selection/edit state cannot be bookmarked or restored after refresh.

### Journey C — Diary detail/history → exact historical Diary

`/site-diary` → RECORDS → Semakan Terdahulu → explicit historical `revisionId` → list query scoped by `programmeId + revisionId` → exact list projection selected by persisted `siteDiaryId` → exact detail/history APIs.

No current-Revision remapping occurs after selection. Switching workspace tabs or refreshing loses the selected historical Revision and exact record view, but does not silently rewrite the record.

### Journey D — Diary/Approval request → queue → exact review → decision

Approval request is triggered within Diary workflow/API behavior; the user then manually selects the in-page Kelulusan tab. Queue query is scoped to `programmeId`. Review carries `approvalId + siteDiaryId`, loads both exact records, checks their Programme/Revision/Activity bond and Pending status, then PATCHes exact `approvalId` with optimistic concurrency.

There is no URL-level Approval queue/review destination and no cross-screen redirect after request. Component-state loss returns the user to RECORDS, not to an incorrect approval.

### Journey E — current/historical Diary → exact Print

Current or historical `DiaryDetail`, and post-save `DailyEntryFeedback`, link to `/site-diary/print?id=<encoded siteDiaryId>`. Print calls the exact authorized API and verifies returned identity. Historical `siteDiaryId` remains sovereign.

The shell header’s generic `/site-diary/print` link omits the mandatory ID and therefore leads to the bounded missing-ID error state. It is not a valid canonical Print handoff.

## 6. Canonical identity hierarchy

The identities form scope, not substitution:

1. **Programme scope — `programmeId`:** selects a Programme intentionally and scopes current Revision resolution, open Activities, Diary lists, and Approval queue. It cannot identify a Revision, Activity, Diary, or Approval.
2. **Revision scope — `revisionId`:** identifies a Programme Revision. Operational creation uses only the latest authorized current Revision. An explicitly selected historical Revision may scope read-only listing, but cannot be converted to current or used to reconstruct a Diary.
3. **Activity identity — `activityId`:** identifies canonical operational Activity state. It may seed/continue a Site Diary entry but cannot replace `siteDiaryId` after persistence.
4. **Exact Diary identity — `siteDiaryId`:** sovereign for detail, edit, history, and Print. Programme/Revision/Activity are validation context, never reconstruction inputs.
5. **Approval identity — `approvalId` plus bonded `siteDiaryId`:** sovereign for exact review/decision. Programme/Revision/Activity bonds must match the canonical Approval and Diary records.

Safe storage based on current evidence:

- Route/query parameters: stable navigation identity, especially `siteDiaryId` for Print and any future exact record route; a future exact Approval route must carry `approvalId` and must validate its bonded Diary rather than trust duplicated query claims.
- Component state: ephemeral UI modes, filters, open panels, and currently selected tabs; never the sole durable identity for a promised deep-link destination.
- Persisted application state: no repository-backed navigation store exists. F2.6 must not add a route-persistence library or use persisted state as authority.
- Programme and Revision context may be represented in URL only if they are explicit scope selectors. They must not override exact record identity.

## 12. Locked navigation contract

### A. Global navigation

Global items represent stable user-facing page destinations only. API routes, mutations, Print, exact review actions, filters, and in-page workflow modes are not global items. Active state is derived from the current route, not from stale component selection.

### B. Programme context

Programme changes must be explicit when more than one Programme is available. A global transition may preserve an explicitly selected `programmeId` only if the destination accepts that scope and revalidates it. It must never default to `prog-1`, silently select the first Programme, or leak one Programme’s state into another.

### C. Revision context

Operational entry resolves the latest authorized current Revision for the selected Programme. Historical Revision selection is explicit read context. Global navigation must not promote historical context to operational context or remap an exact historical record to the current Revision.

### D. Exact record routing

`siteDiaryId` is sovereign for Diary detail, edit, history, and Print. `approvalId` plus its canonical bonded Site Diary context is sovereign for Approval review/decision. Neither may be reconstructed from Programme, Revision, Activity, date, list position, or current state. All dynamic identities are encoded at URL construction and validated at the destination.

### E. Authority

UI visibility and active state are UX. Authentication, Programme membership, capability, record state, and mutation authority remain server/database authoritative and fail closed. F2.6 must not introduce client-side security claims.

### F. Stale context

Every asynchronous context load must have request ownership or cancellation. After Programme, Revision, Activity, Diary, Approval, or route identity changes, response A cannot render, navigate, or mutate state belonging to B.

### G. History

Historical records remain exact, read-only records. No navigation transition may silently redirect or reinterpret them as a current Revision/current Diary. Exiting history must be an explicit user action.

### H. Read/write distinction

Links, tab selection, Programme selection, route changes, active-state calculation, and shell rendering are read/navigation operations. They must not POST, PATCH, archive, approve, start, complete, request approval, or otherwise mutate domain state. Existing explicit action buttons remain outside the navigation contract.

## 13. Test strategy

### Unit

- Pure destination descriptor/active-state logic: exact route matching, no substring collisions, Print classified contextual.
- Programme context transition reducer/helper: explicit switch clears dependent Revision/Activity/Diary/Approval state.
- Responsive destination projection: identical canonical destinations and accessible labels across desktop/mobile presentations.
- URL builders: encoded `programmeId` only where accepted; exact encoded `siteDiaryId`; exact `approvalId` without reconstruction.
