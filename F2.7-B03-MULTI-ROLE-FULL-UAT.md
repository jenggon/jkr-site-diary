## 5. Discovered Defect Classifications (Informational / Non-Blocking to Acceptance)

In accordance with Section 10 of the HQ Directive, the following implementation discrepancies in the baseline product were identified during exploratory testing:

### Defect 1: PostgREST Foreign Key Ambiguity in `GET /api/programme-revision`
- **Classification**: **Class C (Operational Workflow Blocker on Revision Switcher UI)**
- **Affected Endpoints**: `GET /api/programme-revision?programmeId=[id]`
- **Root Cause**: `SiteDiaryManagementReadRepository.ts` queries `.select('..., programme(current_revision_id)')`. In the schema, `programme_revision` references `programme` via `programme_id` and `programme` references `programme_revision` via `current_revision_id`. PostgREST fails with error:
  `"Could not embed because more than one relationship was found for 'programme_revision' and 'programme'"`.
- **Mitigation/Note**: Operational CPM model correctly follows the latest authorised CPM revision resolved via `GET /api/project-summary` (which uses repository `ProgrammeRevisionRepository` and does not use ambiguous PostgREST embedding).

### Defect 2: UI Weather Condition Mapping vs DB Enum
- **Classification**: **Class C (Operational Workflow Blocker on UI Weather Submission)**
- **Affected Components**: `DailyEntryForm.tsx` (line 309)
- **Root Cause**: The UI defaults `weatherCondition` to `'ELOK'` and maps it to `weather = 'Sunny'`. In PostgreSQL, `public.site_diary.weather` is of enum type `activity_weather_session` (`Morning`, `Afternoon`, `Night`). Passing `'Sunny'` triggers PostgreSQL error `invalid input value for enum public.activity_weather_session: "Sunny"`.
- **Mitigation/Note**: When submitted via API contract with `weather: null` and JKR Page 1 print context `weather_condition: "ELOK"`, the atomic transaction succeeds with 201 Created and persists correctly.
