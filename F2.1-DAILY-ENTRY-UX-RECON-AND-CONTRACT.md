## 1. Executive Summary

During F0 and F1, the backend domain engines, database schemas (DB-014, DB-015), API contracts, and the authoritative JKR Site Diary Page 1 visual contract were proven and locked. However, the current user-facing UI remains fragmented across three disparate artifacts:
1. `src/app/site-diary/LegacySiteDiaryPage.tsx`: A 2,928-line legacy prototype with hardcoded Programme IDs, desktop-simulated phone frames, legacy status actions, and no VO support.
2. `src/app/site-diary/F1GoldenPathBridge.tsx`: An interim DOM-interception and `window.fetch` monkey-patching wrapper built during F1 to inject printable context (`print_context`) and lifecycle dates.
3. `src/app/page.tsx`: An experimental "Open Activities Dashboard" that requires users to manually type raw UUIDs.

The mission of **F2.1** is **NOT** a big-bang rewrite of the frontend, nor does it authorise redesigning the domain architecture or inventing new business semantics. The goal is to **incrementally migrate the proven F1 Daily Entry path into modular, mobile-first components, retiring legacy/bridge surfaces only after package-level parity and CI proof**, directly and transparently interacting with the sealed F0/F1 backend APIs.

## 6. Legacy / Redundant UI Findings

1. **`F1GoldenPathBridge.tsx` Fetch Monkey-Patch:** Overrides `window.fetch` at runtime to intercept API calls and inject `print_context`. This was an effective F1 proof shim, but must be replaced by direct form state and API wiring once parity is proven.
2. **Artificial Phone Notch Simulator:** CSS classes `md:rounded-[40px] md:border-8 md:border-zinc-800` and a fake black notch (`w-32 h-6 bg-zinc-800 rounded-full`) create an artificial phone simulation on desktop while hurting real mobile responsiveness.
3. **Legacy Administrative Status Actions:** Buttons for 'Tangguh' (Suspend) and 'Batal' (Cancel) attempt to invoke non-canonical endpoints, conflicting with the locked 3-state physical machine (`New -> In Progress -> Completed`).
4. **Hardcoded Programme IDs:** Hardcoded UUIDs (`0651e125-3ef4-47c4-a3fa-8aec49bdf979` and `prog-1`) prevent multi-project operational use.
5. **Redundant Weather Fields:** Two separate weather controls exist on the same page: a legacy time-of-day selector (`Pagi`, `Petang`, `Malam`) and the authoritative JKR weather condition selector (`ELOK`, `HUJAN`, `MENDUNG`, `RIBUT`).

## 7. Mobile UX Findings (Field Supervisor Perspective)

From the perspective of a site supervisor using a smartphone in the field:
1. **Vertical Fragmentation:** The user must enter "Maklumat Cetakan JKR" in the top bridge box, scroll down past the phone header, enter activity details in the legacy form, and scroll further for manpower.
2. **Missing VO Entry:** If executing Variation Order work, the supervisor cannot select or create a VO item from the phone, forcing them to either abandon the app or misclassify work.
3. **Obtrusive Browser Alerts:** Errors and confirmations trigger native modal `alert()` popups that block mobile interaction.
4. **Unresponsive Manpower Inputs:** Manpower table columns (Bumi, Non-Bumi, Foreign) are cramped horizontally on standard 360px–390px mobile screens, causing accidental touches.
5. **No Direct Path to Print/PDF:** After saving a diary entry, the supervisor has no visible button to view or print the generated JKR Page 1 document.

## 8. Domain / Architecture Guardrail Check

The proposed F2.1 Daily Entry UX strictly respects all sealed invariants:
- **Programme & Revision Ownership:** Enforced on every Activity and Site Diary creation.
- **Current Revision Exclusivity:** Only tasks/VO items from the current authorized revision are selectable.
- **MSP XOR VO Source Model:** Enforced by the UI selector; an Activity references either an MSP Task or a VO Item, never both.
- **No Fake MSP Tasks:** VO items are created natively via `/api/vo-items`.
- **Immutable History & Identity:** Updates preserve `site_diary_id` and do not create duplicate operational rows.
- **Atomic Workforce Mutation:** All manpower entries persist atomically with the Site Diary record.
- **Server-Verified Identity:** All requests propagate the authenticated Supabase bearer.
- **JKR Page 1 Output Contract:** All fields captured directly feed the locked Page 1 renderer.

## 9. Gaps Preventing Coherent Daily Entry

1. **Gap 1: Absence of VO Item UI:** Field supervisors cannot log non-MSP / variation work.
2. **Gap 2: Fragile Bridge Interceptor:** Reliance on `F1GoldenPathBridge` monkey-patching `window.fetch`.
3. **Gap 3: Divided Print Context UI:** Print context is disconnected from the main form inputs.
4. **Gap 4: Hardcoded Context:** Static Programme UUID instead of dynamic context resolution.
5. **Gap 5: Disconnected Mobile Navigation:** No seamless transition between Entry, Open Activities, and Print Preview.
