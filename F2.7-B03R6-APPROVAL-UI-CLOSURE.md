# F2.7-B03R6 — Site Diary Approval Request + Terminal Observation UI Closure Report

## 1. Locked Root Causes

1. **Gap A (P1 Approval Request UI Action Missing)**:
   After a successful Site Diary creation, `DailyEntryFeedback` only rendered Print preview, Aktiviti Terbuka, and Laporan Baharu. There was no user-facing UI action to request approval. As a result, previous test runners bypassed the UI and made direct API calls to `POST /api/approval`.
2. **Gap B (P2 Terminal Observation Surface Missing)**:
   In `ApprovalReview`, upon a successful PATCH approval decision, the component immediately invoked `onSuccess()`, navigating away without giving the authorised reviewer a terminal success surface to visibly inspect the Approved status, site_diary_id, approved_by, and approval comment.
3. **Response Token Capture in CREATE mode**:
   `submitDailyEntry` in CREATE mode did not populate `lastModifiedAt` from the successful `POST /api/site-diary` response payload, which is required as `expected_site_diary_last_modified_at` for approval request concurrency safety.

---

## 2. Architecture Implemented

### Part A — P1 Approval Request
- In `DailyEntryFeedback`:
  - When non-edit Site Diary creation succeeds, the component receives authoritative identity context (`programmeId`, `revisionId`, `activityId`, `siteDiaryId`, `lastModifiedAt`).
  - Renders explicit `"Mohon Kelulusan"` action button.
  - Submits `POST /api/approval` with exact required payload:
    - `programme_id`
    - `revision_id`
    - `activity_id`
    - `site_diary_id`
    - `expected_site_diary_last_modified_at`
  - Zero client actor identity fields sent (`requested_by`, `approved_by`, `actorId`, `userId` remain strictly server-derived).
  - On HTTP 201: Captures `approval_id` and transitions to explicit `"Menunggu Kelulusan"` Pending state indicator, disabling/removing the request button to prevent duplicate submission.
  - On failure: Surfaced safe canonical error and allows manual retry.

### Part B — CREATE Response Token
- In `DailyEntryForm.tsx` (`submitDailyEntry`):
  - In CREATE mode, canonical response token is captured strictly in priority order:
    1. `data.lastModifiedAt`
    2. `data.updated_at`
    3. `data.submitted_at`
  - No timestamp fabrication. Token is stored in state and passed to approval context as `expected_site_diary_last_modified_at`.

### Part C — P2 Terminal Observation
- In `ApprovalReview.tsx`:
  - On successful `PATCH /api/approval/[id]` with `status === 'Approved'`, the returned Approval data is parsed and stored in `terminalApproval` state.
  - Does NOT automatically navigate away.
  - Renders a terminal success surface on the same review page displaying:
    - Status: Approved / Diluluskan
    - Exact `site_diary_id`
    - `approved_by`
    - `approval_comment` (if present)
    - `approval_date`
  - Provides an explicit `"Kembali ke Kelulusan"` button which invokes `onSuccess()`.
  - Non-Approved decisions (Returned / Rejected) preserve existing immediate callback behavior.
