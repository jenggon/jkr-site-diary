## 1. Root Causes & Corrective Adjudication

### A. Root Cause Summary
1. **Gap A (P1 Approval Request UI Action Missing)**:
   After a successful Site Diary creation, `DailyEntryFeedback` previously only rendered Print preview, Aktiviti Terbuka, and Laporan Baharu. There was no user-facing UI action to request approval.
2. **Gap B (P2 Terminal Observation Surface Missing)**:
   In `ApprovalReview`, upon a successful PATCH approval decision, the component immediately invoked `onSuccess()`, navigating away without giving the authorised reviewer a terminal success surface to visibly inspect the Approved status, site_diary_id, approved_by, and approval comment.
3. **Response Token Capture in CREATE mode**:
   `submitDailyEntry` in CREATE mode previously omitted capturing `lastModifiedAt` from the successful `POST /api/site-diary` response payload (`data.lastModifiedAt ?? data.updated_at ?? data.submitted_at`), which is required as `expected_site_diary_last_modified_at` for approval request concurrency safety.

### B. Corrective Hardening (R6-C1 Pass)
1. **Correction A (Retained Approval ID)**:
   `DailyEntryFeedback` adds explicit retained state `approvalId: string | null` (reset on `savedSiteDiaryId` change). On HTTP 201, `DailyEntryFeedback` validates that `createdApproval.approval_id` is a non-empty string, `createdApproval.approval_status === 'Pending'`, and `createdApproval.site_diary_id === approvalContext.siteDiaryId`. The Pending status element deterministically surfaces `data-approval-id={approvalId}`.
2. **Correction B (Safe Bounded Approval Request Errors)**:
   `DailyEntryFeedback` maps failures strictly to safe, bounded domain messages:
   - `401`: `"Sesi telah tamat. Sila log masuk semula."`
   - `403`: `"Tiada kebenaran untuk memohon kelulusan."`
   - `409`: `"Rekod telah berubah. Muat semula sebelum memohon kelulusan."`
   - All other non-201 / malformed / network failures: `"Gagal memohon kelulusan. Sila cuba lagi."`
   - Raw backend error strings, SQLSTATE codes, PostgREST internals, and database error messages are strictly excluded from the DOM.
3. **Correction C (Approved Response Fail-Closed Validation)**:
   `ApprovalReview` strictly validates the PATCH returned Approval data before setting terminal state:
   - `updatedApproval` exists
   - `updatedApproval.approval_id === approvalId`
   - `updatedApproval.site_diary_id === siteDiaryId`
   - `updatedApproval.approval_status === 'Approved'`
   - `updatedApproval.approved_by` is non-empty string
   - If any condition fails, the component does NOT call `onSuccess()`, does NOT render fake terminal success, and sets safe action error: `"Respons kelulusan tidak sah. Muat semula rekod sebelum meneruskan."`
