## 4. Final Architecture and Data Flow

The final production chain is:

```text
DiaryDetail / DailyEntryFeedback
  -> /site-diary/print?id=<encoded siteDiaryId>
  -> PrintSiteDiaryClient
  -> GET /api/site-diary/<encoded siteDiaryId>/print
  -> extractVerifiedIdentity
  -> authenticated Supabase client
  -> SiteDiaryPrintReadRepository.getExact
  -> public.f25_get_site_diary_print_read
  -> private.get_site_diary_print_read
  -> canonical relationship checks + SITE_DIARY_PRINT_READ capability check
  -> mapRawRowToPrintDto
  -> SiteDiaryPrintDto
  -> locked Page 1 renderer
  -> paginateWorkforce
  -> synchronized continuation pages when overflow exists
```

No date-wide report lookup, Activity-only lookup, current-revision reconstruction, or secondary overflow fetch participates in this chain.

## 5. Exact Identity Contract

`siteDiaryId` is the sole canonical print identity.

- `DiaryDetail` renders a print link only when the loaded canonical `detail.site_diary_id` equals the selected projection `siteDiaryId`.
- `DailyEntryFeedback` renders a print link only when an exact `savedSiteDiaryId` exists.
- Both handoffs use `/site-diary/print?id=<encoded siteDiaryId>`.
- `PrintSiteDiaryClient` reads only the `id` query parameter and calls only `/api/site-diary/<id>/print`.
- `validatePrintDto` rejects a response whose `siteDiaryId` differs from the requested ID.
- The repository calls the exact RPC with `p_site_diary_id`.

The canonical path does not use `/api/reports` and does not reconstruct identity from date, `activityId`, `programmeId`, `revisionId`, WBS, task, or VO identity.

## 6. Authorization Boundary

Authorization remains server/database authoritative.

- The API route verifies the request identity with `extractVerifiedIdentity`.
- The authenticated access token creates the Supabase client used by the repository.
- The private RPC resolves the canonical Programme from the persisted Site Diary relationships.
- `private.assert_capability` enforces `SITE_DIARY_PRINT_READ` against that canonical Programme.
- The public RPC is executable only by `authenticated`; the private helper is not directly executable by browser roles.
- UI CTA presence is not treated as authorization.

No browser-side `programme_membership` lookup or duplicated client authorization decision exists in the canonical print workflow.

## 7. Historical Behavior

Historical Site Diaries print through the same exact persisted Site Diary identity and the same B01–B03 implementation as current records.

- Repository mapping derives `isCurrentRevision` by comparing the persisted record revision with `programme.current_revision_id` and derives `isHistorical` without remapping the record.
- Historical records retain their persisted Programme, Revision, Activity, MSP/VO identity, date, print context, and manpower.
- `DiaryDetail` uses the selected canonical historical `site_diary_id` in the print URL.

There is no current-revision substitution, Activity migration, carry-forward, date lookup, or separate historical print renderer.

## 8. Canonical Snapshot Semantics

`mapRawRowToPrintDto` fails closed for missing or mismatched Programme, Revision, Activity, task, and VO context. It also rejects malformed print context and malformed manpower rows rather than silently discarding or coercing canonical evidence.

Persisted MSP task or VO identity supplies WBS/reference and task description fields. The only absent print-context defaults retained are the established F1 defaults: empty location, null optional time/weather fields, and `CONTRACTOR` when the optional scope key is absent.

After C01:

- `diaryStatus` maps from `site_diary.status`;
- `activityStatus` maps only from canonical `activity.status`;
- null Activity status remains null;
- the renderer therefore leaves all work-status cells unselected when canonical Activity status is null.

Approval state is not included in `SiteDiaryPrintDto` and is not used to fabricate print evidence.
