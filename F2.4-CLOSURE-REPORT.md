## Approval Lifecycle Delivered
- **Create / Request** – `a27_create_approval_atomic` inserts a `Pending` approval and writes an audit row.
- **Pending** – stored state awaiting reviewer action.
- **Approved** – `a27_update_approval_atomic` with capability `SITE_DIARY_APPROVAL_APPROVE` transitions to `Approved` and locks the Site Diary.
- **Returned** – capability `SITE_DIARY_APPROVAL_RETURN` moves state to `Returned` with mandatory comment.
- **Returned → Pending Resubmission** – the same `a27_update_approval_atomic` updates the existing approval row (same `approval_id`) when the requester supplies a new payload and the `expected_sd_last_modified_at` token matches; the requester must hold `SITE_DIARY_APPROVAL_REQUEST` capability; no new row is inserted.
- **Rejected** – capability `SITE_DIARY_APPROVAL_REJECT` moves to `Rejected`.
- **Cancelled** – `SITE_DIARY_APPROVAL_CANCEL` governs the supported transition to `Cancelled` according to the executable Approval state machine.

All lifecycle transitions are enforced by the backend/API/SQL contracts. The reviewer UI presents only Approve, Return and Reject controls; Cancel and Resubmit remain backend/API lifecycle capabilities without dedicated reviewer controls.

## Integrity Architecture
- **Site Diary sealing** – `private.f24_assert_site_diary_unsealed` raises `F24_SITE_DIARY_SEALED` if a `Pending` or `Approved` approval exists.
- **Optimistic concurrency / version token** – callers supply `expected_sd_last_modified_at`; mismatches raise `F24_SITE_DIARY_STALE` (HTTP 409). The UI handles 409 by refreshing canonical Approval/Site Diary evidence and does not automatically retry the mutation.
- **Canonical locking** – `SELECT … FOR UPDATE` on the Site Diary row before any mutation.
- **Active‑review multiplicity** – unique index `uq_approval_one_pending_site_diary` guarantees at most one pending approval per diary.
- **SECURITY DEFINER hardening** – F2.4 uses hardened `SECURITY DEFINER` functions for governed privileged database operations. The relevant migrations preserve actor binding, programme/capability checks, fully qualified object references and `SET search_path = ''` where established so definer execution does not become an authorization bypass.

## Approval UX
- **Authorized queue** – `ApprovalQueue.tsx` consumes a Programme‑scoped queue read protected by `SITE_DIARY_APPROVAL_QUEUE_VIEW`.
- **Exact review boundary** – `ApprovalReview.tsx` consumes the dedicated secure exact‑review endpoint and validates Approval/Site Diary identity and canonical Programme, Revision and Activity context before exposing decision controls.
- **Decision controls** – buttons for `Approved`, `Returned`, `Rejected` are presented only for actionable Pending review context; there is **no reviewer UI** for Cancel or Resubmission actions.
- **Request ownership & race protection** – generation/controller ownership prevents stale queue, review and decision completions from mutating newer context.
- **Structured HTTP 409 reconciliation** – 409 handling is status‑driven; the client refreshes canonical evidence and does not automatically issue a second mutation.
- **Governed retry behavior** – transient queue failures expose a bounded retry for the current Programme context, while authority failures remain fail‑closed.
