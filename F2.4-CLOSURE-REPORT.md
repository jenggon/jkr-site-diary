## Approval Lifecycle Delivered
- **Create / Request** – `a27_create_approval_atomic` inserts a `Pending` approval and writes an audit row.
- **Pending** – stored state awaiting reviewer action.
- **Approved** – `a27_update_approval_atomic` with capability `SITE_DIARY_APPROVAL_APPROVE` transitions to `Approved` and locks the Site Diary.
- **Returned** – capability `SITE_DIARY_APPROVAL_RETURN` moves state to `Returned` with mandatory comment.
- **Returned → Pending Resubmission** – the same `a27_update_approval_atomic` updates the existing approval row (same `approval_id`) when the requester supplies a new payload and the `expected_sd_last_modified_at` token matches; the requester must hold `SITE_DIARY_APPROVAL_REQUEST` capability; no new row is inserted.
- **Rejected** – capability `SITE_DIARY_APPROVAL_REJECT` moves to `Rejected`.
- **Cancelled** – SITE_DIARY_APPROVAL_CANCEL governs the supported transition to Cancelled according to the executable Approval state machine.

- All transitions are enforced by the backend/API/SQL contracts. The reviewer UI presents only Approve, Return and Reject buttons; Cancel and Resubmit actions are backend/API capabilities without dedicated UI controls.

## Integrity Architecture
- **Site Diary sealing** – `private.f24_assert_site_diary_unsealed` raises `F24_SITE_DIARY_SEALED` if a `Pending` or `Approved` approval exists.
- **Optimistic concurrency / version token** – callers supply `expected_sd_last_modified_at`; mismatches raise `F24_SITE_DIARY_STALE` (HTTP 409). The API returns a structured 409 response with error code `F24_SITE_DIARY_STALE`; the client must refresh the approval state before retrying.
- **Canonical locking** – `SELECT … FOR UPDATE` on the Site Diary row before any mutation.
- **Active‑review multiplicity** – unique index `uq_approval_one_pending_site_diary` guarantees at most one pending approval per diary.
- **SECURITY DEFINER hardening** – F2.4 uses hardened SECURITY DEFINER functions for governed privileged database operations. Those functions preserve actor binding, capability checks, fully‑qualified object references, and `SET search_path = ''` where established, so definer execution does not become an authorization bypass. Functions: `private.f24_assert_site_diary_unsealed`, `private.f1_update_site_diary_with_workforce_core`, `private.a27_create_approval_atomic`, `private.a27_update_approval_atomic`.

## Approval UX
- **Authorized queue** – `ApprovalQueue.tsx` fetches only approvals where the current user has the required capability.
- **Exact review boundary** – `ApprovalReview.tsx` validates that the fetched record matches the URL parameters and current Site Diary context.
- **Decision controls** – buttons for `Approved`, `Returned`, `Rejected` are presented; there is **no UI** for Cancel or Resubmission actions.
- **Request ownership & race protection** – `decisionGenerationRef` and abort controller ensure a single in‑flight decision per request.
- **Structured HTTP 409 handling** – server returns `409` with specific error codes (`F24_SITE_DIARY_STALE`, `F24_PENDING_APPROVAL_EXISTS`, etc.); the client must refresh the data before retrying.
