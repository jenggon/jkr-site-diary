## Approval Lifecycle Delivered
- **Create / Request** – `a27_create_approval_atomic` inserts a `Pending` approval and writes an audit row.
- **Pending** – stored state awaiting reviewer action.
- **Approved** – `a27_update_approval_atomic` with capability `SITE_DIARY_APPROVAL_APPROVE` transitions to `Approved` and locks the Site Diary.
- **Returned** – capability `SITE_DIARY_APPROVAL_RETURN` moves state to `Returned` with mandatory comment.
- **Returned → Pending Resubmission** – same update function permits a new payload when the token matches.
- **Rejected** – capability `SITE_DIARY_APPROVAL_REJECT` moves to `Rejected`.
- **Cancelled** – capability `SITE_DIARY_APPROVAL_CANCEL` allowed before a reviewer opens the request.

All transitions are enforced by the SQL contracts and reflected in the UI (queue, detail view, decision buttons).

## Integrity Architecture
- **Site Diary sealing** – `f24_assert_site_diary_unsealed` raises `F24_SITE_DIARY_SEALED` if a `Pending` or `Approved` approval exists.
- **Optimistic concurrency / version token** – callers supply `expected_sd_last_modified_at`; mismatches raise `F24_SITE_DIARY_STALE` (HTTP 409).
- **Canonical locking** – `SELECT … FOR UPDATE` on the Site Diary row before any mutation.
- **Active‑review multiplicity** – unique index `uq_approval_one_pending_site_diary` guarantees at most one pending approval per diary.
- **Stale / conflict semantics** – all 409 responses are handled in the UI with retry guidance.

## Identity & Authorization Architecture
- **Auth identity binding** – `extractVerifiedIdentity` extracts `actorId` and `accessToken` for every mutation.
- **User profile / programme membership** – tables `user_profile`, `programme_membership` created by P02 migration.

- **Programme‑scoped capability assertion** – function `assert_capability(actor_id, programme_id, capability_code)` used throughout B02/B03.
- **SECURITY DEFINER hardening** – every PL/pgSQL function runs with definer rights, preventing privilege escalation.

## Approval UX
- **Authorized queue** – `ApprovalQueue.tsx` fetches only approvals where the current user has the required capability.
- **Exact review boundary** – `ApprovalReview.tsx` validates that the fetched record matches the URL parameters and current Site Diary context.
- **Canonical context bonding** – UI checks programme, revision, activity, and site diary IDs before allowing a decision.
- **Decision controls** – buttons for `Approved`, `Returned`, `Rejected`; disabled when state mismatches.
- **Request ownership & race protection** – `decisionGenerationRef` and abort controller ensure a single in‑flight decision per request.
- **Structured HTTP 409 reconciliation** – server returns `409` with specific error codes (`F24_SITE_DIARY_STALE`, `F24_PENDING_APPROVAL_EXISTS`, etc.); UI surface shows a retry prompt.
- **Governed retry behavior** – UI automatically reloads the approval after a conflict.
