## 1. Locked Defect & Root Cause

### The Defect
When an authenticated user (such as P1 Site Supervisor) performed `GET /api/activity/[activityId]`, the route verified the caller identity successfully via `extractVerifiedIdentity(request)`. However, the route handler instantiated `ActivityRepository` using:
```typescript
new ActivityRepository(new SupabaseDatabaseAdapter(supabase));
```
where `supabase` is the global anonymous client instance initialized with `NEXT_PUBLIC_SUPABASE_ANON_KEY`.

Consequently, the verified caller's `identity.accessToken` was discarded before the read operation. PostgREST executed the query against table `public.activity` with role `anon` instead of `authenticated`, triggering PostgreSQL RLS rejection:
`ERROR: permission denied for table activity (HTTP 500)`

This blocked the frontend client during daily entry continuation mode when verifying authoritative server activity status before `POST /api/site-diary`.

### The Architecture Resolution
In alignment with accepted C09 architecture:
1. `GET /api/activity/[activityId]` creates a request-scoped authenticated Supabase client using `getSupabaseAuthenticatedClient(identity.accessToken)`.
2. The authenticated client is supplied to `SupabaseDatabaseAdapter` and `ActivityRepository`.
3. Error messages on 5xx failures are strictly sanitized to generic safe responses (`"Failed to retrieve activity"`), preventing leakage of SQLSTATE or internal database error messages.
4. Unauthenticated requests return `401 Unauthorized`.
5. Non-existent or RLS-inaccessible activities return `404 Activity not found`.
