## 1. Defect Analysis & Architectural Principle

### The Defect
Prior to this remediation, `DailyEntryForm.tsx` mapped human-readable atmospheric weather conditions (`ELOK`, `HUJAN`, `MENDUNG`, `RIBUT`) to legacy atmospheric strings (`Sunny`, `Rainy`, `Cloudy`, `HeavyRain`) and sent them in the top-level `weather` property of the `POST /api/site-diary` and `PATCH /api/site-diary/[id]` request payloads.

However, the PostgreSQL column `public.site_diary.weather` is typed as enum `public.activity_weather_session` with valid semantic values:
- `Morning`
- `Afternoon`
- `Night`

When PostgreSQL atomic mutation function `private.a27_mutate_site_diary_core` executed:
```sql
nullif(p_payload->>'weather','')::"public"."activity_weather_session"
```
the cast failed with fatal PostgreSQL Error `22P02`:
`ERROR: invalid input value for enum public.activity_weather_session: "Sunny"`

### The Architectural Resolution (HQ Decision)
**Atmospheric weather condition** and **weather session** are fundamentally distinct operational concepts:
1. **Atmospheric Condition**: Represents meteorological weather during work execution (`ELOK`, `HUJAN`, `MENDUNG`, `RIBUT`). It canonically belongs in `print_context.weather_condition` (Format JKR Page 1).
2. **Weather Session**: Represents operational time shifts/sessions (`Morning`, `Afternoon`, `Night`).
3. **Remediation**: The form/request composition layer in `DailyEntryForm.tsx` passes `weather: null` (omitting atmospheric values from the legacy session field) while strictly preserving `print_context.weather_condition` with the selected canonical atmospheric condition (`ELOK`, `HUJAN`, `MENDUNG`, `RIBUT`).
