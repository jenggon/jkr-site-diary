# AGENT LOCKSET PROTOCOL

**Status:** Mandatory for all AI recon, audit, implementation and remediation work.

## Purpose

The active product lockset is the durable record of accepted Product Owner decisions that must survive across chats, agents, refactors and CI changes.

Canonical file:

`docs/00_Governance/ACTIVE_LOCKSET.json`

Canonical execution/proving baseline:

`docs/00_Governance/EXECUTION-PROVING-BASELINE.md`

The lockset supplements, and never overrides, the Project Constitution, ADRs, Business Rules, Domain Documentation or AGENTS.md.

When `ACTIVE_LOCKSET.json` contains `activeProgramme.roadmap`, that roadmap is mandatory execution-order authority for the active programme. It must be read during preflight and included in the compliance acknowledgement. The roadmap may narrow stage order, proving and integration gates, but cannot override higher architecture/business authority or silently supersede a LOCKED requirement.

The execution/proving baseline is mandatory operating-process authority when present. It governs role ownership, workspace alignment, local execution, challenge, preprove, freeze/promotion and official-CI behaviour. It cannot weaken product/domain authority or silently supersede a LOCKED requirement; conflicting accepted process requirements must be resolved through explicit lockset supersession.

## Mandatory workspace alignment preflight

Before producing a governance ACK for a governed implementation/remediation mission, the local executor MUST prove that its workspace is aligned to the expected governed branch/HEAD supplied by Klopp/HQ.

The execution contract must provide:

```text
EXPECTED_BRANCH=<branch>
EXPECTED_GOVERNED_HEAD=<sha>
PROTECTED_LOCAL_PATHS=<paths or NONE>
```

The executor records the current branch, `LOCAL_HEAD_BEFORE` and working-tree status, then fetches origin and compares the local state with the exact expected governed target.

Automatic alignment is permitted only when:

1. the current branch equals `EXPECTED_BRANCH`;
2. the expected governed SHA resolves exactly after fetch;
3. no unauthorised tracked local modifications make alignment unsafe;
4. the incoming commit range does not add, modify or delete a declared protected local path;
5. local HEAD is either already equal to `EXPECTED_GOVERNED_HEAD` or is an exact ancestor of it;
6. alignment can complete with fast-forward only.

Permitted update mechanism:

```text
git fetch origin
# inspect branch/status/incoming diff/ancestry
git merge --ff-only origin/<expected-branch>
```

A generic `git pull` is not the governed mechanism because local Git configuration may introduce merge/rebase behaviour.

The following are forbidden during automatic alignment:

- `git reset` or `git reset --hard`;
- `git clean`;
- `git stash`;
- forced checkout or forced branch movement;
- automatic rebase;
- merge commits;
- deleting, moving, adding or normalising protected local evidence to make alignment succeed.

STOP and escalate to Klopp/HQ when the branch is wrong, local HEAD is ahead, histories diverge, unsafe tracked changes exist, an incoming commit touches a protected local path, the expected SHA cannot be resolved exactly, `--ff-only` cannot complete, or any safety fact is ambiguous.

After successful/no-op alignment, the executor MUST re-read the aligned governance authority and run the normal lockset preflight from `LOCAL_HEAD_AFTER`. A stale pre-alignment lockset result is not a valid ACK.

The first section of an implementation/remediation executor report must include alignment fields before the normal lockset fields:

```text
WORKSPACE ALIGNMENT ACK
EXPECTED_BRANCH=<branch>
WORKSPACE_ALIGNMENT=<PASS|NONE_REQUIRED|STOP>
LOCAL_HEAD_BEFORE=<sha>
EXPECTED_GOVERNED_HEAD=<sha>
LOCAL_HEAD_AFTER=<sha>
ALIGNMENT_MODE=<FAST_FORWARD|NONE|STOP>
PROTECTED_PATH_STATUS=<UNCHANGED|STOP>
```

The desired convenience interface is `pnpm run exec:preflight`. Until implemented, equivalent checks are mandatory explicitly.

## Mandatory governance preflight

After workspace alignment, before an agent performs recon, audit, implementation, remediation, test repair or CI repair, it MUST:

1. Read `AGENTS.md`.
2. Read `docs/00_Governance/AI_CONSTITUTION.md`.
3. Read `docs/00_Governance/PROJECT-CONSTITUTION.md`.
4. Read `docs/00_Governance/ACTIVE_LOCKSET.json`.
5. Read `activeProgramme.roadmap` when present.
6. Read `docs/00_Governance/EXECUTION-PROVING-BASELINE.md` when present.
7. Run `pnpm run lockset:verify` and capture both `LOCKSET_VERSION` and `LOCKSET_HASH`.
8. Identify the active programme/stage when present.
9. Identify the requirement IDs affected by the requested work.
10. Identify all requirement IDs and no-change boundaries that must remain untouched.

`LOCKSET_HASH` is a canonical semantic JSON hash generated by `scripts/verify-lockset.mjs`. It is intentionally independent of CRLF/LF line endings, indentation and JSON object key formatting so the same commit produces the same handshake hash on Windows, Linux and macOS.

The normal governance acknowledgement MUST then be:

```text
LOCKSET COMPLIANCE ACK
BRANCH=<branch>
HEAD=<sha>
LOCKSET_VERSION=<version>
LOCKSET_HASH=<sha256>
ACTIVE_PROGRAMME=<id or NONE>
ACTIVE_STAGE=<stage or NONE>
ROLE=<RECON|AUDIT|IMPLEMENTATION|REMEDIATION>
AFFECTED_IDS=<comma-separated IDs or NONE>
PROTECTED_IDS=<comma-separated IDs>
NO_CHANGE_BOUNDARIES=<summary>
```

If the agent cannot establish workspace alignment or this ACK, it MUST STOP. Work without both applicable preflight gates is invalid evidence.

If an active programme roadmap defines ordered stages, the agent MUST stop when the requested work would skip an unresolved earlier stage or prematurely cross a blocked integration/release gate.

## Product decision capture

Explicit Product Owner decisions that lock, accept, change, supersede, freeze, keep or forbid behaviour must be captured in `ACTIVE_LOCKSET.json` before the next implementation is considered complete.

Accepted requirements are never silently deleted. If an accepted requirement changes:

1. mark the old entry `SUPERSEDED`;
2. set `supersededBy` to the replacement requirement ID;
3. add the replacement requirement as `LOCKED`;
4. increment `locksetVersion`;
5. run `pnpm run lockset:verify`;
6. update tests/evidence where the accepted behaviour changed.

An additive process hardening that does not contradict an existing locked requirement may be captured as an additional `LOCKED` requirement with an incremented lockset version.

Only Product Owner / Chief Architect authority may approve a requirement change. An agent may report that a lock conflicts with implementation, but may not rewrite the lock to fit code.

## Execution ownership baseline

The default role split is defined in `docs/00_Governance/EXECUTION-PROVING-BASELINE.md`.

In summary:

- Product Owner owns product/process decisions requiring authority, remote mutation/promotion authorisation where required, and physical acceptance. The Product Owner is not the routine shell/test/Git operator.
- Klopp/HQ owns governance, context, expected governed branch/HEAD, impact analysis, bounded execution contracts, adjudication, review and gate control.
- Codex is the default local working-tree executor when attached to the repository and executes only the bounded contract, including the authorised fast-forward-only alignment preflight.
- Agentic challenge is read-only by default; when Codex implemented, Antigravity is preferred as the independent challenger when available.
- CI confirms/proves the already-preproved exact candidate; it should not be used as the routine first discovery environment for deterministic candidate defects.

No executor or challenger may self-elevate into Product Owner or Chief Architect authority.

## Recon and audit rules

Recon and audit are read-only unless a later explicit implementation instruction is issued.

Reports MUST evaluate implementation against the lockset, execution/proving baseline and active programme roadmap, not the reverse. Findings must name the affected requirement IDs.

A stale test, selector or implementation detail that conflicts with a current LOCKED requirement is subordinate to the lock and must not be treated as authority merely because it existed earlier.

## Implementation rules

Before editing, implementation agents MUST produce or receive a `LOCKED REQUIREMENT IMPACT MATRIX` containing:

- active programme/stage when present;
- affected requirement IDs;
- protected requirement IDs;
- files expected/allowed to change;
- files/domains forbidden to change;
- verification evidence required after the change.

The executor must also receive an execution contract that states the expected branch, expected governed HEAD, protected local paths, allowed files, forbidden files/domains, bounded change intent, targeted evidence, preprove evidence and whether commit/push authority has been granted.

If implementation requires changing a LOCKED requirement or no-change boundary, STOP and escalate before editing.

The Product Owner must not be used as the default manual patch applier or test/Git operator merely because the current assistant lacks direct local working-tree access. Use the authorised local executor or explicitly escalate the tooling limitation.

## Targeted test, challenge and preprove rules

After implementation/remediation:

1. run the smallest authoritative targeted test/browser gate for the intended change;
2. if red, keep the failure pre-official, adjudicate and return to bounded implementation;
3. after targeted green, use a read-only agentic challenge when risk warrants it;
4. resolve/dispose findings through Klopp/HQ;
5. run complete stage-aware preprove before the candidate may freeze;
6. a preprove red remains pre-official and returns to adjudication/repair;
7. only an all-green exact candidate is eligible to freeze and promotion authority.

The desired steady state is a canonical stage-aware `pnpm run preprove:<stage>` command used by both the local executor and official CI wherever technically possible. Until such a command exists, all equivalent required gates must be executed explicitly; convenience-command absence never removes a gate.

## Official CI red classification

Official CI is confirmation/proof of the already-preproved exact candidate.

Every official red must be classified at minimum as:

- `PRODUCT_DEFECT`;
- `HARNESS_DEFECT`;
- `ENVIRONMENT_PARITY`;
- `GOVERNANCE_PREFLIGHT`;
- `INFRASTRUCTURE`.

A candidate-caused official red is not followed by a blind fix-and-push. Reproduce or explain the failure, repair it pre-official, return to full green preprove, freeze the new exact SHA, then promote again under the required authority.

Existing active-programme red-loop thresholds remain authoritative: 0 excellent; 1 classify; 2 process miss requiring workflow/recon review; 3+ stop repeated proving and improve the mechanism before another attempt.

## No green-by-bypass rule

CI green is valid only when the evidence remains equal or stronger.

The following are forbidden as a means of making CI green unless the Product Owner / Chief Architect explicitly approves a justified replacement with equal-or-stronger evidence:

- `force: true` to bypass user actionability;
- skipped or deleted assertions protecting a LOCKED requirement;
- relaxed geometry, overflow, identity, authority or state thresholds;
- hiding or moving an interfering overlay instead of testing the intended runtime;
- arbitrary timeout inflation;
- adding retries to mask deterministic failure;
- opening internal state or URLs to avoid a required user interaction;
- replacing real-browser evidence with source-string presence checks;
- changing production behaviour solely to satisfy a faulty harness.

When a harness is wrong, repair the harness while preserving or strengthening the original requirement evidence.

## Required completion report

An implementation or remediation report is not complete without:

1. workspace alignment result including local-before / governed-target / local-after SHAs;
2. exact branch and HEAD;
3. `LOCKSET_VERSION` and `LOCKSET_HASH`;
4. active programme/stage when present;
5. affected requirement IDs;
6. explicit statement that protected IDs, protected local paths and no-change boundaries remained intact;
7. targeted test result;
8. agentic challenge result/disposition where required;
9. full stage-aware preprove result, including full `pnpm run verify` and the applicable real-browser gate where required;
10. `git diff --check` / bounded-scope review result where applicable;
11. exact frozen candidate SHA when freeze has occurred;
12. official CI result and red classification if any;
13. physical acceptance status where required;
14. explicit disclosure of any remaining red or unverified gate.

`CI GREEN` alone is never equivalent to `SEALED`.
