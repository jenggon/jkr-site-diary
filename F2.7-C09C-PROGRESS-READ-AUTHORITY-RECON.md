## 6. Exact Read-Authority Questions & Answers

1. **Can a legitimate authenticated Programme member DIRECT SELECT from `public.progress` through Data API?**
   - **YES** (Technically available because `public.progress` does not have RLS enabled and SELECT was not revoked; however, it lacks Programme-membership RLS filtering).

2. **Does a sanctioned read RPC or view exist for Progress?**
   - **NO**. There are zero read RPCs (e.g. no `f24_get_progress_review` or equivalent) and zero read views for Progress in the canonical schema.

3. **Is the current Progress atomic mutation boundary sanctioned?**
   - **YES**. `public.a27_create_progress_atomic` and `public.a27_update_progress_atomic` are canonical `SECURITY DEFINER` public wrappers granted to `authenticated`, which independently assert `auth.uid() = p_actor_id`, active revision, context linkage, cumulative bounds, and atomic audit logging.

4. **Does `ProgressService` currently lose caller context on reads for which direct authenticated SELECT IS already sanctioned?**
   - **YES**. For `activity`, `programme_revision`, and `site_diary`, direct authenticated SELECT is sanctioned under C07 RLS policies (`c07_programme_member_select_*`), but `createProgressService` instantiates prerequisite repositories with default/global unauthenticated clients rather than request-scoped authenticated clients.

5. **Does `ProgressService` require a read for which NO sanctioned read mechanism currently exists?**
   - In `ProgressService.validateCumulativeCeiling()`, it attempts a read on `public.progress`. While direct SELECT is not revoked by SQL permissions, no governed/sanctioned RLS policy (such as `c07_programme_member_select_progress`) or read RPC was ever established.
