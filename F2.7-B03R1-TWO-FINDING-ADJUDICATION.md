## 2. Finding 1 Adjudication: Programme Revision Resolution

### A. Static Call Graph & Flow Analysis
- **Route Definition**: `src/app/api/programme-revision/route.ts` (GET)
- **Repository Method**: `SiteDiaryManagementReadRepository.findRevisions(programmeId)`
- **Query**:
  ```typescript
  .from('programme_revision')
  .select('revision_id, programme_id, revision_no, revision_title, status, programme(current_revision_id)')
  .eq('programme_id', programmeId)
  .order('revision_no', { ascending: false })
  ```
- **PostgREST Schema Failure**:
  In PostgreSQL, `programme_revision` references `programme` via `programme_id` (FK `programme_revision_programme_id_fkey`) AND `programme` references `programme_revision` via `current_revision_id` (FK `programme_current_revision_id_fkey`).
  PostgREST throws runtime error:
  `"Failed to retrieve Programme Revisions: Could not embed because more than one relationship was found for 'programme_revision' and 'programme'"`
  Additionally, column `revision_title` does not exist on table `programme_revision` (the column name is `revision_name`).

### B. UI Callers & Operational Dependency Assessment
1. **P1 Normal Site Diary Creation Flow**:
   - `DailyEntryShell.tsx` (line 157): Calls `/api/project-summary?programmeId=${targetId}` to resolve the operational CPM revision (`summaryData.revision_id`).
   - `DailyEntryShell.tsx` (line 182): Calls `/api/programme/${targetId}` to enrich programme metadata (`programmeCode`, `programmeName`).
   - `DailyEntryForm.tsx`: Calls `/api/activities/open?programmeId=...` (`OpenActivitiesList`) and `/api/task/revision/...` (`OperationalSourceSelector`).
   - **Result**: Normal P1 Site Diary creation does NOT call `/api/programme-revision`.
2. **P2 Approval Queue & Review Flow**:
   - `ApprovalQueue.tsx`: Calls `/api/programme/${programmeId}/approval-queue`.
   - `ApprovalReview.tsx`: Calls `/api/approval/${approvalId}/review` and `/api/site-diary/${siteDiaryId}`.
   - **Result**: Normal P2 Approval workflow does NOT call `/api/programme-revision`.
3. **Where `/api/programme-revision` is called**:
   - `DiaryManagementList.tsx` (line 106): Mounted on `RECORDS` tab (`Rekod / Sejarah`) to populate optional revision switcher filter.
   - `DiaryDetail.tsx` (line 62, line 112): Historical detail inspector to resolve revision title.
4. **Current Operational Revision Resolution Path**:
   `DailyEntryShell` -> `fetch('/api/project-summary?programmeId=...')` -> `ProgrammeService.getProjectSummary` -> `ProgrammeRevisionRepository.findActiveRevision` -> resolves `current_revision_id` directly from `public.programme` without PostgREST embedding.

### C. Finding 1 Adjudication Answers
1. Is `/api/programme-revision` called by the normal P1 Site Diary UI journey? **NO**.
2. Is it called by normal P2 Approval Queue / Review journey? **NO**.
3. Does current B03 operational current-revision resolution instead use another sanctioned boundary such as `/api/project-summary`? **YES** (`/api/project-summary?programmeId=...`).
4. Can P1 perform Programme discovery -> current Revision resolution -> Open Activity discovery -> Site Diary UI entry without `/api/programme-revision`? **YES**.
5. Is the endpoint itself defective when directly invoked? **YES**.
