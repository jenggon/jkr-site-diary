## 2. Finding 1 Adjudication: Programme Revision Resolution

### A. Core Question & Adjudication Verdict
> *Does the failure of `GET /api/programme-revision?programmeId=<id>` actually block the CURRENT accepted B03 product journey?*

**Verdict**: **NO**. The endpoint is genuinely defective when invoked directly, but the canonical B03 operational journey (Programme Discovery -> CPM Current Revision Resolution -> Open Activity Selection -> Daily Entry Creation -> Approval Queue & Review) does not traverse or depend upon this endpoint.

### B. Static Call Graph & Flow Analysis
- **Route Implementation**: `src/app/api/programme-revision/route.ts` (GET handler)
- **Repository Implementation**: `SiteDiaryManagementReadRepository.findRevisions(programmeId)` (`src/repositories/SiteDiaryManagementReadRepository.ts` line 68)
- **Database Query**:
  ```typescript
  this.client
    .from('programme_revision')
    .select('revision_id, programme_id, revision_no, revision_title, status, programme(current_revision_id)')
    .eq('programme_id', programmeId)
    .order('revision_no', { ascending: false });
  ```
- **Root Cause of Endpoint Defect**:
  1. **Dual Foreign Key Ambiguity**: In the schema, `programme_revision` references `programme` via FK `programme_revision_programme_id_fkey` (`programme_id`), while `programme` references `programme_revision` via FK `programme_current_revision_id_fkey` (`current_revision_id`). PostgREST fails with error:
     `"Could not embed because more than one relationship was found for 'programme_revision' and 'programme'"`.
  2. **Schema Drift**: The query selects non-existent column `revision_title` (the actual column on `programme_revision` is `revision_name`).

### C. Caller Analysis Across Operational Roles
1. **Normal P1 Site Diary Creation Journey**:
   - `DailyEntryShell.tsx` (line 157) establishes programme context by querying `/api/project-summary?programmeId=${targetId}`.
   - It extracts `summaryData.revision_id` directly from the project summary payload.
   - `DailyEntryShell.tsx` (line 182) enriches metadata via `GET /api/programme/${targetId}`.
   - `DailyEntryForm.tsx` mounts `OpenActivitiesList` (`GET /api/activities/open?programmeId=...`) and `OperationalSourceSelector` (`GET /api/task/revision/...`).
   - **Result**: Normal P1 daily entry flow does NOT call `/api/programme-revision`.
2. **Normal P2 Approval Queue & Review Journey**:
   - `ApprovalQueue.tsx` queries `GET /api/programme/${programmeId}/approval-queue`.
   - `ApprovalReview.tsx` queries `GET /api/approval/${approvalId}/review` and `GET /api/site-diary/${siteDiaryId}`.
   - **Result**: Normal P2 approval flow does NOT call `/api/programme-revision`.
3. **Where `/api/programme-revision` is Actually Called**:
   - `DiaryManagementList.tsx` (line 106): Mounted on the optional `RECORDS` tab (`Rekod / Sejarah`) to populate a revision filter dropdown.
   - `DiaryDetail.tsx` (line 62, line 112): Historical detail inspector modal to resolve revision title.
4. **Current Operational Revision Resolution Path**:
   `DailyEntryShell` -> `fetch('/api/project-summary?programmeId=...')` -> `ProgrammeService.getProjectSummary` -> `ProgrammeRevisionRepository.findActiveRevision` -> resolves `current_revision_id` directly from `public.programme` without ambiguous PostgREST embedding.
