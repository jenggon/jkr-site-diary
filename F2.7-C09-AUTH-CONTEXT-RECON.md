## B. Static Call Graph — C09-A (Site Diary Flow)

### B.1 Route Entry Point: `POST /api/site-diary` (`src/app/api/site-diary/route.ts`)
1. **Identity Extraction**:
   - Calls `extractVerifiedIdentity(request)` (`src/app/api/_shared/identity.ts`).
   - Extracts `identity.accessToken` (Bearer token) and `identity.actorId` (via `getSupabaseServerClient().auth.getUser(accessToken)`).
   - If missing or invalid token, returns `401 Unauthorized`.
2. **Payload Parsing & Validation**:
   - Validates JSON body against `createSiteDiarySchema` via Zod.
   - Requires `isValidUuid` for `programme_id`, `revision_id`, and `activity_id`.
   - Requires `isValidIso8601` for `activity_date`.
   - Validates `operation_intent`, `notes`, and optional `print_context`.
3. **Service Composition**:
   - Calls `createSiteDiaryService(identity.accessToken)` (`src/composition/siteDiaryComposition.ts`).
   - Instantiates `SiteDiaryService` with dependencies:
     - `programmeRepository`: `new ProgrammeRepository()` (**UNAUTHENTICATED / ANON**)
     - `revisionRepository`: `new ProgrammeRevisionRepository()` (**UNAUTHENTICATED / ANON**)
     - `siteDiaryRepository`: singleton import `siteDiaryRepository` (**UNAUTHENTICATED / ANON**)
     - `activityRepository`: constructor default `new ActivityRepository()` (**UNAUTHENTICATED / ANON**)
     - `atomicRepository`: `new ResidualAtomicRepository(getSupabaseAuthenticatedClient(accessToken))` (**AUTHENTICATED / REQUEST-SCOPED**)
     - `clock`: `new SystemClock()`
     - `logger`: `new Logger({ module: 'SiteDiaryService' })`

## F. Hypothesis Classification

- **C09-A (Site Diary Prerequisite-Read Context)**: **UNPROVEN**
  - *Reason*: In canonical clean reset state, the available Programme and Revision fixtures use synthetic repeated-digit UUIDs (`111...`, `333...`) which are rejected at the route edge by Zod's `isValidUuid` schema validation (`HTTP 400`). Because no semantically RFC-valid Programme fixture exists in seed and fixture modification is prohibited, the prerequisite-read service layer cannot be reached through the real HTTP route under canonical state.
- **C09-B (Approval Prerequisite-Read Context)**: **CONFIRMED**
  - *Reason*: Real HTTP requests to `POST /api/approval` and `PATCH /api/approval/[approvalId]` by properly authenticated callers (P1, P2) with legitimate Programme authority fail with `HTTP 500` (`42501 permission denied`) at prerequisite reads (`ProgrammeRevisionRepository.findById` and `approvalRepository.getApprovalById`) before reaching the atomic mutation boundary, solely because the composition layer instantiates prerequisite repositories with the unauthenticated anon client rather than propagating the verified caller's authenticated token.

## G. Minimal Remediation Hypothesis (Architecture Commentary Only)
> [!NOTE]
> This is architectural commentary only. Per mission rules, NO code or database changes are implemented.

1. **Approval Composition Root (`src/composition/approvalComposition.ts`)**:
   - Replace module-level unauthenticated singletons (`revisionRepository`, `activityRepository`, `siteDiaryRepository`, `progressRepository`, `approvalRepository`) with request-scoped factories that construct these repositories using the caller's authenticated Supabase client (`getSupabaseAuthenticatedClient(accessToken)` or an authenticated database adapter).
2. **Site Diary Composition Root (`src/composition/siteDiaryComposition.ts`)**:
   - Propagate `accessToken` into `ProgrammeRepository`, `ProgrammeRevisionRepository`, `ActivityRepository`, and `siteDiaryRepository` so all prerequisite reads execute within the caller's authenticated security context under C04/C07 RLS.
3. **Fixture / Route Schema Alignment**:
   - Harmonize canonical seed fixture UUID formats to adhere to RFC 4122 variant 1, ensuring acceptance tests and real application routes evaluate against valid fixtures end-to-end.
